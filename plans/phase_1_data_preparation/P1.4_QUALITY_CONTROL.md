# P1.4 POD 品質控制

## 目的

P1.4 不會刪除或修改原始 POD。它讀取 `swarm_a_states` 與 P1.3 的
`swarm_a_orbital_elements`，把每一筆資料的可用性寫入新的
`swarm_a_pod_quality`。

這張表是後續 P1.5 的唯一入口：平滑與 10 分鐘重採樣只能使用
`is_usable = 1` 的資料。

## 資料形狀

```text
swarm_a_pod_quality
{
  time_us,
  is_usable,
  rejection_reason,
  interval_id
}
```

- `time_us`：連回同一時間的原始 POD。
- `is_usable`：`1` 是可用，`0` 是不可用。
- `rejection_reason`：不可用時的固定英文原因；可用時是 `NULL`。
- `interval_id`：可用資料所屬的連續區間。

## P1.4-A：單筆資料有效性

目前先實作不需要猜測門檻的規則。

| 規則 | 條件 | `rejection_reason` |
| --- | --- | --- |
| Q1 | 時間不遞增 | `time_not_increasing` |
| Q1 | 位置或速度是空值、NaN、無限大 | `non_finite_state` |
| Q5 | P1.3 沒有對應的半長軸結果 | `missing_orbital_element` |
| Q5 | P1.3 判定軌道能量無效 | `invalid_orbital_energy` |
| Q5 | 半長軸是空值、NaN、無限大或不為正 | `invalid_orbital_element` |

P1.3 已在 GCRF 中檢查 radius、specific energy 與 bound orbit；P1.4 直接使用
那個結果，不再重做昂貴的座標轉換。

## 尚未實作的 P1.4 部分

| 規則 | 為何暫緩 |
| --- | --- |
| Q3 ESA quality flag | 要先確認 SP3 產品是否真的有逐筆 quality flag。 |
| Q4 maneuver candidate | 要先從正常區間的 position/velocity residual 校準門檻。 |

這些不是漏做；它們目前缺少可辯護的判定依據。先填入任意門檻會把正常的
storm-time drag 誤判成壞資料。

## 執行與驗證

執行：

```powershell
python -m satellite_orbit.data.prep_derived_pod_quality
```

測試：

```powershell
python -m unittest tests.test_prep_pod_quality
```

測試涵蓋一筆正常資料、NaN、缺少 P1.3 結果，以及 P1.3 拒絕的能量狀態。

## P1.4-A 實際結果

已對目前 SQLite 中的 14,558,400 筆 POD 執行一次檢查：

| 項目 | 筆數 |
| --- | ---: |
| 原始 POD | 14,558,400 |
| P1.3 半長軸 | 14,558,400 |
| P1.4-A 品質結果 | 14,558,400 |
| `is_usable = 1` | 14,558,400 |
| 被拒絕 | 0 |

所以原始資料目前沒有 Q1/Q5 能辨識的壞列。這個結論不會取代後續的
gap、maneuver 與 interval 檢查。

## P1.4-B 連續區間結果

`swarm_a_states` 的實測 native cadence 是 10 秒。任何同一個來源檔內
超過 10 秒的相鄰時間差都會切開 interval；每個 source-file boundary 也一定
切開 interval。

| 項目 | 結果 |
| --- | ---: |
| 可用資料的 interval | 1,685 |
| 每個 interval 的 POD 筆數 | 8,640 |
| interval 內發現的 time gap | 0 |
| `is_usable = 1` 但沒有 `interval_id` | 0 |

所以目前的每個 interval 正好對應一個原始 POD 來源檔。Q3 與 Q4 尚未完成；
未來若發現 quality failure 或 maneuver candidate，該資料點前後會再切出新的
interval。
